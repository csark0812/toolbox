# Ownership sessions

<!-- source-of-truth: human adoption state and continuation -->
<!-- doc-meta: owner=eng | last-reviewed=2026-09-30 -->

Keep a session record of target/input identity, current part, intent, decisions and per-part status: unseen, accepted, change-requested, needs-recheck or deferred. Record supporting source and evidence for acceptance.

Explain one meaningful part through review-walkthrough. Classify each concern as verified defect, design preference or uncertain, with evidence. Ask accept/change/defer only for this explicit adoption flow. For authorized structural changes dispatch refactor-companion; non-code work uses its artifact editor. Verify changes and resume the same causal position.

On source changes identify affected covered parts. Preserve accepted intent and unaffected decisions; invalidate changed implementation acceptance and proof. Show material differences and renew acceptance where the implementation no longer matches what was accepted. Offer affected earlier parts without moving the current cursor automatically. End with each part accepted, explicitly deferred or explicitly pending. Editing success alone is not human acceptance.

An uncertain issue sent to code-review is an independent question. A disliked but viable abstraction is a preference, not a defect. Process lessons are proposals for skill evolution, separate from product decisions.
